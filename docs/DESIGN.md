## Problem Statement

用户的 API key / 密钥 / 配套 URL 高度碎片化，散落在环境变量、笔记、文档、邮件、各家后台等多个地方。三样本该绑在一起的信息（厂商、用途、key、url）是分开存的，导致两个具体痛点：
1. 取用麻烦——主要在浏览器/后台界面里复制粘贴 token 和 url，找到 key 还得再跑一趟文档去捞对应 url。
2. 找回麻烦——位置混乱，经常在好多地方找 key；有时攥着一个 key 却不知道它对应什么使用场景（缺用途名称），不知道用在哪里。

现有方案（KeePassXC、pass、1Password、Bitwarden、Doppler/Infisical/Vault）要么是"账号+密码"的形状、把 url 和"用途"当二等公民，要么是面向团队/云端的重型工具。没有一个专门为"厂商 + 用途 + api_key + url"这一新形状（人手十几个大模型/API 厂商的 key）做收纳与找回。这个缺口就是本项目的机会。

## What Makes This Cool

让"用途 + api_key（+ 厂商 + url + 备注 + 标签）"作为一个不可分割的整体存在一个地方：存的时候逼你把用途和 key 配齐，取的时候一次拿全、一键复制，永远不用再去别处对照。把通用密码管理器的盲区（url 和用途不是一等公民）变成本工具的核心卖点。

在此之上，用三条腿解决"位置混乱、不知道用在哪"：

- **厂商作为分组维度（不只是文本字段）。** 录入时从已有厂商里选择，没有则新建，不用手打。这消灭"DeepSeek / deepseek / 深度求索"这类拼写不一致把同一厂商拆成几堆的问题；列表可按厂商折叠分组浏览。
- **标签作为跨厂商的横切分类。** 厂商回答"谁家的"，标签回答"干嘛用的 / 哪个项目 / 是否已废弃"。同一标签（如 `翻译`、`项目A`、`已废弃`）可贴在不同厂商的 key 上，按标签筛选。与必填的"用途名称"不冲突——用途名称是该记录的名字，标签是可跨记录复用的筛选维度。
- **关键字搜索。** 即时过滤用途名称 / 备注 / 厂商。

三者并存：厂商分组浏览、标签筛选、关键字搜，覆盖"我记得是某厂的""我要找某用途的""我只记得名字一部分"三种找回路径。

## Constraints

- 完全本地优先；数据出门走云之前必须已加密（加密是不可妥协的底线）。
- 单人自用工具，先不做团队/共享/权限。
- "可分享"指代码开源或给朋友自己装来用，不是多人协作同一份库。
- 同步外包给第三方网盘（坚果云 / WebDAV / Dropbox 等），不自建后端。
- 主力平台 Windows（用户环境 Win 11）；跨平台分发为加分项。

## Premises（已与用户逐条确认）

1. 核心价值 = 收纳与找回；加密是不可妥协的底线（要走云，必须先加密）。— 同意
2. 每条记录字段：**用途名称 + api_key 必填**；厂商、url、备注、标签可留空。存时对必填字段做校验。厂商为"分组型"字段（从已有项选择或新建，非自由手打）；标签为多值、跨记录复用的横切分类。— 同意（用户修正：只有用途名称和 api_key 必填，其余可空；后续补充：厂商作分组、增加标签维度）
3. 同步走"本地加密文件 + 网盘搬运"，不自建后端；安全靠"出门前已加密"，云只当不识字的搬运工。— 同意
4. 单人工具，先不做共享。— 同意

## Approaches Considered

### Approach A: 本地桌面 App（带搜索界面）— 选定
能双击打开的小程序，左侧搜索框+列表，右侧显示某条记录全部字段，每字段后带"复制"按钮。打开需主密码解锁。数据存为单个加密文件，放进网盘同步目录。
- Effort: M / Risk: 低
- Pros: 场景 2/3 体验天花板（搜得到、看得清、url 与 key 各一个复制键，一次拿全）；录入时强制"用途+key 必填"治碎片化；朋友双击即用，分享门槛最低。
- Cons: 开发量最大（界面、打包、主密码解锁流程）；跨平台分发要各打包。
- Reuses: 成熟加密库（AES-GCM / libsodium / age 一类）；网盘做同步。

### Approach B: 命令行工具（CLI）
`keyvault add` / `keyvault find deepseek` / `keyvault get <名称> --copy`（进剪贴板）。同一个加密文件，同样丢网盘。
- Effort: S / Risk: 低
- Pros: 开发量最小、最快可用；搜索/复制对终端用户极快；跨平台几乎免费（单二进制）。
- Cons: 场景 2 在浏览器后台复制粘贴，需在终端和浏览器间切换，体感不如点一下；给非技术朋友分享门槛高。

### Approach C（横向）: 浏览器插件 + 本地加密库
点插件图标弹搜索框，搜到记录把 url/key 一键填入当前页输入框或复制。数据仍是本地加密文件。
- Effort: L / Risk: 中
- Pros: 场景 2 极致形态（key 就在要粘贴的页面里，零切换）；分享叙事最性感。
- Cons: 插件读写本地加密文件 + 网盘同步那条链最别扭、工程坑最多；安全面最大（key 活在浏览器环境）；开发调试成本最高。更像 v2。

## Recommended Approach

**Approach A（本地桌面 App）。** 两个核心场景（后台界面复制粘贴、找回）都吃"视觉搜索 + 一眼看全 + 一键复制"，正是图形界面强项；CLI 在场景 2 会逼用户在终端/浏览器间反复切换；插件体验上限最高但同步链是工程噩梦，留作以后。A 在方便/易管理/可分享三项综合最稳，开发量可控（M）。A 与 B 可共用同一加密文件格式，日后若发现自己泡在终端可低成本补 B。

## Open Questions

- 桌面技术栈未定（Tauri / Electron / 原生 .NET WinUI / 其他）—— 留给 /plan-eng-review。注意：若选 .NET WinUI 等 Windows 专属栈，等于放弃"跨平台为加分项"，需二选一。
- 加密文件格式与字段 schema 的具体设计 —— 留给 plan。需保证加密格式与 KDF 跨平台一致（否则跨平台分发破功）。
- **主密码丢失 = 数据永久不可读。** 单人本地加密工具的固有取舍：默认无恢复机制。需决定是否提供"恢复码 / 明文导出备份"等逃生口，或明确接受"丢主密码即丢全部"。这是用户最可能踩的坑，应在设计层有明确答案。
- **备份策略。** 网盘同步 ≠ 备份——误删或文件损坏会被同步传播到所有设备。单点加密文件损坏 = 全丢。需决定是否提供本地多版本/导出备份。
- **多设备冲突处理。** 网盘对加密文件无法自动合并，会产生"冲突副本"（如 `xxx (冲突).kdbx`），用户可能误开旧副本。纯靠"用前先同步、勿在两台同时编辑"的约定很脆弱（网盘同步有延迟）。倾向：打开时检测文件 mtime/版本，提示"可能未同步完成"，成本低且比纯约定可靠。是否内置留待 plan。
- **唯一性 / 标识。** 用途名称是否要求唯一？两条同名记录（如都叫"翻译"）如何区分、`get <名称>` 取哪条？倾向用内部 ID 做主键、用途名称允许重名但搜索时全列出。留待 plan。
- 解密后明文的泄漏面（剪贴板、内存、临时文件）：一键复制进系统剪贴板与"剪贴板自动清空"的时序要协调好（清空不能早于用户粘贴）。安全细节留给 plan。
- 解锁失败次数限制、空库/无搜索结果等边界态 —— 留给 plan。

## Success Criteria

- 录入一条记录时，用途名称和 api_key 缺失会被阻止/提醒；厂商、url、备注、标签可留空。
- 厂商以分组形式呈现：录入时可从已有厂商中选择或新建，无需手打；列表可按厂商分组浏览。
- 支持给记录设置多个标签，并能按标签筛选/检索；标签可跨不同厂商的记录复用。
- 支持对已有记录的修改和删除（厂商轮换 key 是长期使用必然需求），不只是录入。
- 能按用途名称/厂商/标签关键字即时过滤定位某条记录（数据量预计 <100 条，无性能压力）。
- 一条记录的 api_key 与 url 各能一键复制，无需去别处对照。
- 数据文件在写入磁盘/进入网盘目录前已加密；无主密码无法读取。
- 同一加密文件放入网盘后，能在用户的另一台电脑上解锁并读到相同数据。

## 工程决策（/plan-eng-review on 2026-06-17）

四个地基决策已锁定，互相咬合自洽：

- **D1 技术栈：Tauri 2（Rust 后端 + 系统 WebView）。** 安全工具最看重小攻击面 + 成熟加密库 + 跨平台，三者全占。前端 HTML/CSS/JS，核心逻辑/加密在 Rust。
- **D2 加密：AES-256-GCM + Argon2id（RustCrypto 的 aes-gcm + argon2 crate）。** Argon2id 是 2026 OWASP 首选 KDF。绝不自己手搓算法。salt/nonce 管理要做对，nonce 每次加密唯一。
- **D3 数据格式：单个加密 JSON blob。** 顶层放元数据（格式版本、KDF 参数、salt）+ 记录数组；启动整读进内存，改动整写回（原子写）。与"整文件加密+云盘搬运"天然契合。**明确排除 SQLCipher**——活 SQLite 文件增量写入+WAL 副文件，与云盘同步冲突会损坏库。
- **D4 多设备冲突：打开/保存时检测文件哈希变化。** 保存前重读磁盘文件，若在编辑期间被别的设备改过就弹警告让用户选覆盖/放弃，不静默覆盖、不自动合并（自动合并是 v2）。
- **D5 加密测试：完整含 KAT 固定向量。** 防"改了 KDF 参数/编码导致老库静默解不开"这一加密工具特有回归。
- **D6 逃生口：v1 加明文导出（二次确认）+ 保存前自动留本地旧版副本。** 主密码丢失明确不可恢复。

ASCII — 多设备冲突故障场景（D4 要拦的）：

```
A机: 解密→改key→加密写回 vault.enc
      │ (云盘还在上传, 没传完)
B机: 打开旧 vault.enc→改url→写回
      │
云盘: 同一文件两处改 → "vault(冲突副本).enc"
结果: 一台的改动静默丢失   ← D4 在保存前比对哈希拦住它
```

## NOT in scope（v1 明确不做）

- **自建后端/同步服务** — 同步外包给坚果云等网盘，安全靠"出门前已加密"。
- **团队/共享/多人协作同一库** — 单人工具。
- **自动逐条冲突合并** — D4 只做检测+警告，自动合并留 v2。
- **SQLCipher/数据库** — 与云同步模型冲突，已用 JSON blob 替代。
- **CI 跨平台打包发布流水线** — 记入 `TODOS.md`，本地跑通后再做。
- **支持上千/上万条记录的性能优化** — 数据量 <100，JSON blob 足够。

## Failure modes（每条新代码路径的生产故障）

| 路径 | 故障方式 | 有测试? | 有错误处理? | 用户可见? |
|------|---------|--------|-----------|----------|
| 解密 | 错误主密码 | ✓ (T3) | ✓ 干净失败 | ✓ 清晰报错 |
| 解密 | 密文被篡改 | ✓ (T3) | ✓ GCM 拒绝 | ✓ 报错 |
| KDF | 升级改了参数→老库解不开 | ✓ KAT(T3) | — | ✓ 测试红 |
| 保存 | 编辑期间文件被别设备改 | ✓ (T6) | ✓ 警告 | ✓ 选择覆盖/放弃 |
| 保存 | 写到一半崩溃 | T4 原子写 | ✓ 临时文件+rename | 数据不损坏 |
| 库文件 | 云盘误删/损坏 | T9 | ✓ 本地旧版副本 | 可恢复 |
| 主密码 | 丢失 | ✓ (文档) | 不可恢复(设计取舍) | ✓ 明文导出逃生口 |

无静默失败的关键路径——D4 冲突检测正是为了消灭"静默丢数据"这个唯一会咬人的故障。

## 并行化策略

```
Lane A (地基, 顺序): T1 scaffold → T2 crypto → T3 crypto-test  (共享 src-tauri/crypto)
Lane B (数据层, 顺序, 依赖 A 的 crypto): T4 vault → T5 CRUD → T6 conflict → T9 backup (共享 src-tauri/vault)
Lane C (前端, 部分并行): T7 核心交互 → T8 分组标签 / T11 首次运行 (共享 src/)
Lane D (依赖全部): T12 E2E
```

执行顺序：A 先行（地基）。A 出 crypto 后 B 可启动。C 可与 B 并行（前端 mock 数据先做界面）。最后 T12 E2E。
冲突标记：Lane C 内 T7/T8/T11 都动 `src/`，建议顺序或细分子目录避免合并冲突。

## 设计决策（/plan-design-review on 2026-06-17）

分类：**App UI**（工作区型、数据密集、任务导向），适用 App UI 规则——平静的表面层级、强排版、少颜色、少装饰，卡片只在"卡片本身就是交互"时才用。

### D2 主界面：三栏布局（筛选 / 列表 / 详情）

```
┌─────────────────────────────────────────────────────────────┐
│  🔍 搜索用途/厂商/备注...                      [+ 新增]  [⚙]  │  顶部:搜索常驻+主操作
├──────────────┬──────────────────────────────────────────────┤
│ 全部 (42)     │   DeepSeek · 翻译用                            │  详情面板:选中项全字段
│ ─────────    │   ┌────────────────────────────────────────┐ │
│ ▾ 厂商        │   │ api_key  sk-xxxx...xxxx        [复制] 👁 │ │  key 默认遮罩,点睛显示
│   DeepSeek(3)│   │ url      https://api.deep...   [复制]    │ │  url 独立复制键
│   OpenAI (5) │   │ 厂商      DeepSeek                        │ │
│   Claude (2) │   │ 标签      #翻译  #项目A                   │ │
```

信息层级：搜索框 + 左栏筛选器是第一眼（治"位置混乱"），中间列表第二，详情面板第三。厂商分组和标签都是**常驻筛选器**而非两个竞争的视图——搜索按文本缩小、左栏点击按厂商/标签缩小，三者叠加。

### D3 空状态（两种区分对待）

- **首次空库**：一句欢迎语 + 大的"新增第一个密钥"主按钮 + 一行提示该填什么（用途、key）。引导开始，不是冷冰冰"暂无记录"。
- **搜索/筛选无结果**："没找到匹配 X 的记录" + 一个"清除筛选"按钮给出口。

### D4 复制反馈 + 剪贴板清空

点复制后：按钮瞬间变"✓ 已复制"维持约 1.5s，底部出一条提示"api_key 已复制，× 秒后自动清空剪贴板"。明确告知复制成功 + 何时会清，用户不用猜。与 D-工程 的剪贴板延迟清空（防泄露）配套——清空倒计时可见。

### D5 最小设计代头（无 DESIGN.md，锁这三个防 slop 漂移）

- **字体**：一款真正文字体（非 system-ui/Inter/Arial 默认栈）+ 一款**等宽字体专门渲染 api_key / url**（等宽让密钥字符串更好认、更难看错）。
- **主色**：一个强调色（非紫蓝渐变默认），其余走中性灰阶。
